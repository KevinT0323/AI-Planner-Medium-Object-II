## L22201 數據收集與清理

### 第 1 題［高難｜CDC 去重與亂序事件］

某資料庫以 CDC 將訂單變更傳至分析平台，傳送語意為 at-least-once。每筆記錄包含 `order_id`、`op`（`INSERT/UPDATE/DELETE`）、來源資料庫單調遞增的 `source_lsn`、`event_time` 與 `ingest_time`。由於網路重試，同一個 `source_lsn` 可能重複出現；不同變更也可能亂序抵達。

平台要重建「來源位置 `source_lsn = 900` 時」的訂單表，且不得讓已刪除的訂單復活。下列何種做法最正確？

A. 每個 `order_id` 保留 `ingest_time` 最晚的非 `DELETE` 紀錄  
B. 先依 `event_time` 排序，再將所有 `DELETE` 紀錄捨棄  
C. 先依唯一變更識別碼（例如主鍵加 `source_lsn`）去除重送；對每個 `order_id` 選取 `source_lsn <= 900` 中位置最大的變更，若該變更為 `DELETE` 則不輸出該訂單  
D. 對每個 `order_id` 只選取 `source_lsn <= 900` 中最大的非 `DELETE` 變更

### 第 2 題［高難｜事件時間視窗與 SQL 邊界］

某交易模型的特徵定義為：對每筆目標交易 `t`，加總同一客戶在事件時間區間 `[t.event_time - 10 分鐘, t.event_time)` 內的過去交易金額。任何與目標交易同一 `event_time` 的交易均不得使用。

客戶 C1 有以下交易：

| event_time | amount |
|---|---:|
| 09:59 | 5 |
| 10:00 | 10 |
| 10:04 | 20 |
| 10:09 | 30 |
| 10:10 | 40 |

對 10:10 這筆目標交易，哪一個 SQL 條件與數值組合正確？

A.

```sql
p.customer_id = t.customer_id
AND p.event_time >= t.event_time - INTERVAL '10 minutes'
AND p.event_time <  t.event_time
```

特徵值為 60。

B.

```sql
p.customer_id = t.customer_id
AND p.event_time BETWEEN t.event_time - INTERVAL '10 minutes'
                     AND t.event_time
```

特徵值為 100。

C.

```sql
p.customer_id = t.customer_id
AND p.event_time >  t.event_time - INTERVAL '10 minutes'
AND p.event_time <= t.event_time
```

特徵值為 90。

D. 依 `ingest_time` 選取目標交易前 10 分鐘的資料，特徵值為 65。

### 第 3 題［高難｜Schema Drift 與資料契約］

物流設備的舊版訊息以 `distance_m` 表示整數公尺；新版改用 `distance` 與 `unit`（`m` 或 `km`），少數異常訊息會缺少版本或出現未知單位。下游需要穩定的「公尺」欄位來訓練模型。何種收集與清理設計最妥當？

A. 對所有數值計算 z-score，超過 3 就假定是公里並自動除以 1,000  
B. 直接將新舊欄位串接為字串，讓模型自行學習單位  
C. 依當前整批資料的中位數猜測每筆的單位，且不保留原始訊息  
D. 用 schema registry／資料契約識別版本，依明示單位轉為 canonical `distance_m`；保留原始訊息與版本，對缺版本、未知單位或越界值標記品質狀態並隔離，同時監測異常率

### 第 4 題［中偏難｜串流文字特徵擷取］

搜尋系統每日收到大量新詞，詞彙持續成長；訓練與線上服務都要將查詢文字轉成固定維度的稀疏向量，且不能因每個新詞擴張字典。何種方案最符合要求？

A. 每日以當日全部資料重新 `fit` 一個不限大小的詞彙表，線上立即切換而不記錄版本  
B. 採用固定 `n_features` 的 feature hashing，訓練與服務共用相同的 tokenizer、hash 函式與維度，並監測碰撞；若加入 IDF，則將只由訓練資料估計的 IDF 參數版本化  
C. 直接使用 Python 進程的內建 `hash()` 而不固定任何設定，並假設每個進程的映射都相同  
D. 對每個新詞動態新增一個 one-hot 欄位，並讓各服務實例自行維護欄位順序

## L22202 數據儲存與管理

### 第 5 題［高難｜MVCC 與 Write Skew］

排班資料庫有兩位值班工程師 A、B，目前 `on_call=true`，業務不變量是「至少一人必須值班」。兩個交易都在 snapshot isolation 下開始：T1、T2 各自讀到兩人都值班；T1 將 A 改為 `false`，T2 將 B 改為 `false`。因為更新不同資料列，兩者都成功 commit，最後無人值班。何者最正確？

A. 這是 write skew；可使用真正的 serializable isolation 並對 serialization failure 重試，或以能讓兩交易產生衝突的鎖定／不變量實體化設計保護該條件  
B. 這是 dirty read；把隔離級別降為 READ UNCOMMITTED 即可避免  
C. 這是同一列的 lost update；只替 `on_call` 建普通單欄索引即可保證至少一人值班  
D. 這表示 MVCC 無法提供任何一致讀取；將讀取改到非同步 replica 就會自動維持不變量

### 第 6 題［高難｜BRIN 範圍索引］

PostgreSQL 中的 `telemetry` 是一張 120 億列的 append-mostly 表，資料的物理順序與 `event_time` 高度相關。常見查詢是「掃描某一天的所有記錄」，且索引儲存預算極低。何種索引選擇最符合此工作負載？

A. 對 `event_time` 建立 hash index，因為 hash index 最擅長時間範圍  
B. 對每一列都建立一個另外的 covering B-tree，且忽略寫入與空間成本  
C. 對 `event_time` 建立 BRIN，依物理相關性調整 `pages_per_range`，並監測資料亂序對排除效果的影響  
D. 對 `event_time` 只建立全文檢索，並將時間先轉為任意文字

### 第 7 題［高難｜Quorum 一致性計算］

某複製式鍵值儲存對每個 key 保存 `N = 5` 份 replica。在無 sloppy quorum、沒有並行衝突，且讀取會依版本選擇最新值的前提下，系統要求：

何組讀 quorum `R` 與寫 quorum `W` 同時滿足要求？

A. `R = 2, W = 3`  
B. `R = 3, W = 3`

### 第 8 題［高難｜Bitemporal 與可重現訓練］

客戶風險等級資料在 3 月 15 日才收到更正：客戶 C1 其實自 2 月 1 日起應為 Gold，但系統在更正前一直記為 Bronze。團隊既要精確重現 3 月 1 日當時已知資料所訓練的模型，也要能用現在已更正的事實重新產生資料集。何種設計最適合？

A. 直接將 Bronze 覆寫為 Gold，不保留更正前版本

D. 同時儲存「業務上何時生效」的 valid-time 區間與「系統何時知道該版本」的 system-time 區間，並以資料 snapshot／版本作為訓練基準

## L22203 數據處理技術與工具

### 第 9 題［高難｜Spark Catalyst 與架構式解析］

Spark 工作每天讀取依 `event_date` 分割的 Parquet 事件，只需近 7 日的 `user_id` 與 JSON `payload.score`。現行作法先對所有列執行 Python UDF 解析 JSON，再過濾日期，CPU 與 Python/JVM 序列化成為瓶頸。哪一項改寫最可能同時利用 partition pruning、column pruning 與 Catalyst 優化？

A. 先對全部欄位執行 Python UDF，完成後才呼叫 `filter` 與 `select`  
B. 先以內建欄位運算過濾 `event_date` 並只選所需欄位，再使用明確 schema 的 `from_json` 與內建表示式取出 `score`  
C. 將原始 DataFrame `collect()` 到 driver，以單一 Python 進程解析後再建回 DataFrame  
D. 先將全部歷史欄位 `cache()`，每天仍對所有列執行同一 Python UDF

### 第 10 題［高難｜Kafka 交易與處理語意］

一個 Kafka 處理器從 `input` topic 消費，產生轉換結果至 `output` topic，並推進原 consumer group 的 offsets。若進程可能在任何時點崩潰，下列何種方案最能避免「結果已寫但 offset 未推進」或「offset 已推進但結果未寫」？

A. 處理前先 commit offsets，之後再寫 `output`

### 第 11 題［高難｜Watermark 與視窗狀態］

某 Spark Structured Streaming 工作使用事件時間的 5 分鐘 tumbling windows，視窗區間為 `[start, end)`，允許延遲為 10 分鐘。某時已觀測到最大事件時間 10:20，因此 watermark 已達 10:10。本題將狀態清理規則明確設為：當 `window_end <= watermark` 時就結算並移除狀態，之後抵達、隸屬已移除視窗的事件會被捨棄。

現在依序抵達：

- E1：`event_time = 10:09:30`
- E2：`event_time = 10:10:00`
- E3：`event_time = 10:14:59`

何者正確？

A. E1、E2、E3 都接受，因為事件時間均不晚於 10:20  
B. E1 接受；E2 因恰好落在 watermark 而捨棄；E3 接受  
C. E1 隸屬 `[10:05, 10:10)` 且該視窗已移除，因此捨棄；E2 與 E3 隸屬 `[10:10, 10:15)`，因此仍可接受  
D. E1、E2、E3 都捨棄，因為它們是在 watermark 產生後才抵達

### 第 12 題［高難｜分散式精確 Global Top-K］

一個分散式批次作業將 100 億筆、分布於 200 個 partitions 的候選項目，依確定性 `score` 取全域最高 100 筆。分數相同時可以唯一 `item_id` 作穩定決勝。何種方法可得到精確結果，且顯著降低傳至 coordinator 的資料量？

A. 每個 partition 依 `(score, item_id)` 先取本地 top 100，最多傳回 `200 × 100 = 20,000` 筆，coordinator 再用同一決勝規則取 top 100  
B. 每個 partition 只傳本地 top 1，coordinator 將 200 筆當成全部候選  
C. 每個 partition 各自計算項目的「本地名次」，coordinator 取名次平均最小的 100 筆  
D. 每個 partition 隨機抽樣 100 筆後合併，因為樣本數達 20,000 就必然精確
