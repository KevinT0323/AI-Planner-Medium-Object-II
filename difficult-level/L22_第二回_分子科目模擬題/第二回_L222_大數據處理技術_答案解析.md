## L22201 數據收集與清理

### 第 1 題：C

`source_lsn` 代表來源資料庫的變更順序，才是重建指定來源位置應使用的權威排序鍵。先以變更識別碼去重，再選取 cutoff 以前每個主鍵的最大 LSN；最後一個變更若為 tombstone，就表示該列在該位置不存在。

- A 錯在使用抵達時間：舊變更可因重試更晚到達，並將已刪除資料復活。
- B 錯在把業務時間當成資料庫 commit 順序，且捨棄刪除訊號。
- D 故意忽略最後的 `DELETE`，會留下本應不存在的舊版本。

### 第 2 題：A

半開區間 `[10:00, 10:10)` 包含 10:00 的下邊界，不包含 10:10 的目標時點，因此加總 `10 + 20 + 30 = 60`。SQL 的 `>=` 與 `<` 恰好實作該邊界語意。

- B 的 `BETWEEN` 兩端都包含，會把 10:10 的目標交易算入，造成目標洩漏。
- C 同時排除 10:00 並包含 10:10，與特徵定義相反。
- D 使用收錄時間會讓傳輸延遲改變特徵，並非題目定義的事件時間視窗；65 也是將視窗外的 09:59 誤納入才得到的值。

### 第 3 題：D

單位與欄位語意屬於資料契約，不應由數值大小猜測。正確流程是識別 schema 版本、依明示規則轉為單一 canonical unit，並將無法安全轉換的資料隔離，而不是靜默編造值。保留 raw payload、schema 版本與品質狀態，也才能稽核與回放。

- A 把業務單位問題誤當統計離群值；合法的長距離也可能被誤改。
- B 未建立一致數值語意，下游無法穩定計算。
- C 以批次分佈猜單位不可驗證，且丟棄原始訊息後無法追查或重新清理。

### 第 4 題：B

Feature hashing 不需先建立完整詞彙，能將未見新詞映射至固定維度，並維持稀疏表示。但線上與離線必須共用完全相同的文字切分、hash 算法、維度與符號規則。Hashing 本身可無狀態，IDF 則是由訓練 corpus 學得的狀態，必須分開版本化並避免使用驗證／未來資料估計。

- A 會造成維度無界成長與訓練—服務欄位錯位。
- C 的進程內建 hash 不適合當跨進程特徵契約，預設隨機化可使映射不一致。
- D 仍會讓維度持續增長，各實例自行排列更會使欄位語意不一致。

## L22202 數據儲存與管理

### 第 5 題：A

兩個交易都讀到相同的合法 snapshot，卻更新不同資料列，因此沒有直接的 write-write conflict；各自判斷合法，合併結果卻破壞跨列不變量，這就是 write skew。真正的 serializable isolation 能偵測這類無法序列化的相依，應用程式則需準備重試被中止的交易。

另一類做法是重新設計衝突點，例如在交易內鎖住代表整體排班規則的共同資料列，或把不變量實體化成可由資料庫約束／鎖定的結構。降低隔離級別只會更弱；普通索引不會建立跨列不變量；非同步 replica 可能更舊，不能解決問題。

### 第 6 題：C

BRIN 儲存每組物理 block range 的摘要，當 `event_time` 與物理位置高度相關時，可用很小的索引排除大量不相關頁面。`pages_per_range` 在索引大小與摘要精度間取捨；若資料逐漸亂序，BRIN 的排除能力也會下降。

- A 的 hash index 主要支援等值查找，不適合時間範圍。
- B 的 B-tree 可支援範圍，但在 120 億列上建立大型逐列索引，不符合題目的極低空間預算；「對每欄建 covering index」更無必要。
- D 的全文檢索是為語言 token 搜尋設計，不是數值／時間範圍索引。

### 第 7 題：B

為保證讀取與已成功寫入的 quorum 必有交集，需 `R + W > N`。又因最多只有 3 個 replica 可用，讀與寫的 quorum 都必須不大於 3。`R=3, W=3` 同時滿足 `3+3>5` 與兩者的可用性要求。

- A 的 `R+W=5`，兩集合可能剛好互不重疊，不能保證讀到最近成功寫入的 replica。
- C 雖然有交集，但寫入要 5 個 replica，任一 replica 不可用就無法寫。
- D 雖有交集，但讀取要 4 個 replica，有 2 個不可用時無法讀。

### 第 8 題：D

Bitemporal 模型分開兩種時間：valid time 描述資訊在業務世界何時為真，system time 描述系統何時收到／儲存該版本。因此，「以 3 月 1 日當時所知」重現時，可限制 system-time cutoff；使用現在更正後的事實時，則可採最新 system-time 版本，同時仍依 prediction time 做 valid-time join。Snapshot／版本識別碼則使整個訓練資料集可稽核。

- A 破壞歷史，無法重現當時所知資料。
- B 只能表達事實生效區間，無法分辨系統在不同時點知道哪一個版本。
- C 把後來才獲得的知識當成當時已知，無法重現歷史訓練輸入。

## L22203 數據處理技術與工具

### 第 9 題：B

先以 partition column 的內建表示式過濾，能讓 Spark 在檔案掃描前做 partition pruning；只選取必要欄位可進一步做 column pruning。使用明確 schema 的 `from_json` 與內建表示式，Catalyst 能理解運算結構，也可避免大量 Python/JVM 跨進程序列化。

- A 對大量最後會被過濾的資料先付出 UDF 成本，且 Python UDF 對 optimizer 較不透明。
- C 將分散式大資料收回 driver，會失去平行度並有 OOM 風險。
- D 緩存全歷史不會消除不必要的解析與序列化成本，還增加快取壓力。

### 第 10 題：D

Kafka 的交易式 consume–process–produce 可將輸出 records 與輸入 offsets 的推進綁在同一個交易：不是兩者一起可見，就是兩者都不 commit。`read_committed` 可防止下游讀到中止交易的輸出。生產環境還要正確處理 producer fencing、transaction timeout 與 rebalance。

- A 若在 offset commit 後、寫出前崩潰，會永久遺失結果。
- B 若在寫出後、offset commit 前崩潰，重啟後會重複寫出。
- C 的 producer idempotence 只解決 producer retry 的部分重複，沒有將 consumer offsets 與輸出原子化。

> 這項保證是 Kafka 交易範圍內的。若同時寫入不支援同一交易的外部資料庫，仍需外部 sink 的冪等 key、upsert 或對應的交易協調。

### 第 11 題：C

E1 的 10:09:30 落在 `[10:05, 10:10)`，這個視窗的 `end=10:10`，已滿足 `window_end <= watermark`，所以狀態已移除，E1 被捨棄。E2 恰好在半開區間的新視窗下邊界，與 E3 都隸屬 `[10:10, 10:15)`；該視窗的 `end=10:15` 仍大於 watermark，狀態未移除。

- A 忽略了 watermark 是用來限制可保留的舊視窗狀態，不是只比較事件是否早於最大時間。
- B 誤解 `[start,end)` 邊界；10:10:00 是新視窗的 start，不是舊視窗的成員。
- D 把「在 watermark 後抵達」誤當成「一律捨棄」；應判斷事件隸屬視窗的狀態是否已移除。

### 第 12 題：A

任一筆全域 top 100 項目，必定也位於自己 partition 的本地 top 100：若它在本地連前 100 都進不去，已有至少 100 個全域中同樣存在的項目排在它前面，它不可能是全域 top 100。因此合併 200 份 local top 100 不會遺漏真正答案，傳輸量上限為 20,000 筆。兩層都用相同 `(score, item_id)` 全序關係，可保證同分時也可重現。

- B 最多只保留每區一筆，若多個全域高分項目在同一 partition，會遺失第 2～100 名。
- C 的本地名次無法在分數分佈不同的 partitions 間當成可比分數。
- D 隨機抽樣只能做近似，無法保證包含任何一筆全域 top 100。
